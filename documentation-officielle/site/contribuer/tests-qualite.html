Tests et qualité

Chaque projet du monorepo a ses propres commandes de vérification. La CI (.github/workflows/ci.yml) les rejoue sur chaque pull request, en ne lançant que les jobs des projets modifiés. Cette page donne, projet par projet, ce qu'il faut lancer avant de pousser et ce que la CI exige pour qu'une pull request soit fusionnable.

#Avant d'ouvrir une pull request

Une commande par projet modifié, les mêmes que dans CONTRIBUTING.md. Elles rejouent en local l'essentiel des contrôles de la CI.

Terminal
cd backend && npm run typecheck && npm run lint && npm run env:check && npm test
Terminal
cd frontend-web && npm run lint && npm run typecheck && npm test
Terminal
cd mobile-app && npm run typecheck && npm run lint
Terminal
cd smart-contract && npm run lint && npm run test:coverage && npm run coverage:check
Terminal
cd documentation-officielle && npm run check

Pour l'Office de Tourisme, depuis frontend-office-tourisme/ :

Terminal
node ../.github/scripts/check-static-links.mjs .

#Vue d'ensemble de la CI

flowchart LR
    CH["changes : dossiers modifiés"] --> BE["backend"]
    CH --> SC["contracts"]
    CH --> WE["web"]
    CH --> MO["mobile"]
    CH --> TO["tourisme"]
    SC --> CI["chain : backend sur un vrai nœud"]
    BE --> CI
    BE --> DO["docker : images, Compose, Trivy"]
    SC --> DO
    WE --> DO
    TO --> DO
    GL["secrets : gitleaks"]
    DOC["documentation"]
Job Se lance si Durée maximale
changes toujours 5 min
secrets toujours 10 min
documentation toujours 10 min
backend backend/** modifié 15 min
contracts smart-contract/** ou backend/** modifié 20 min
chain contrats ou backend modifiés, et contracts et backend sans échec 20 min
web frontend-web/** modifié 15 min
mobile mobile-app/** modifié 15 min
tourisme frontend-office-tourisme/** modifié 5 min
docker infrastructure, backend, contrats, web ou tourisme modifiés, et les jobs précédents sans échec 20 min

Une modification de .github/workflows/ci.yml déclenche tous les jobs. Le job contracts tourne aussi quand seul le backend change, parce que le backend embarque les ABI des contrats. Toutes les actions GitHub sont épinglées par empreinte de commit (actions/checkout@11d5960a...) et non par étiquette, ce qui empêche une étiquette déplacée d'injecter du code dans la CI.

La liste générée des jobs est dans Intégration continue.

#Tests unitaires et d'API

Les tests de backend/__tests__/ appellent l'application Express avec Supertest. Prisma et Redis y sont remplacés par des doublures en mémoire (prisma.mock.ts, redis.mock.ts) ; setup-env.ts force BLOCKCHAIN_MODE=simulated et désactive le code de connexion par email et la double authentification des administrateurs. Ces tests n'ont donc besoin ni de base, ni de Redis, ni de blockchain.

Attention

La doublure Prisma est écrite à la main : elle ne connaît que les modèles et les méthodes déjà utilisés. Un nouveau modèle ou une nouvelle méthode Prisma (groupBy, aggregate...) appelés dans une route testée demandent d'étendre prisma.mock.ts, sinon le test échoue sur une fonction indéfinie.

#Tests sur une vraie blockchain

Le job chain construit l'image de smart-contract/, qui démarre un nœud Hardhat, déploie les contrats et lance un oracle VRF local, puis exécute npm run test:chain avec PostgreSQL et Redis réels. Le scénario de onchain-lottery.chain.ts couvre l'achat, le cadeau, l'avance du temps (evm_increaseTime), le tirage par le keeper, le versement de la cagnotte, le POAP et le disjoncteur. En local :

Terminal
docker compose up -d --wait
cd backend && npm run test:chain

Voir Tests sur une vraie chaîne.

Danger

Le dossier mobile-app/__tests__/ contient trois fichiers de tests (compte à rebours, écran d'achat, formateurs), mais le projet n'a ni script test, ni Jest dans ses dépendances. Ces tests ne sont exécutés nulle part. Les rendre exécutables demande d'ajouter jest, jest-expo et @testing-library/react-native, un script test et l'étape correspondante dans le job mobile.

#Documentation

npm run check, depuis documentation-officielle/, construit le site dans un dossier temporaire, le compare à site/, vérifie les liens, les ancres et les descriptions des tableaux générés. Le job tourne sur chaque pull request, même sans modification de la documentation, parce qu'un changement du code peut rendre une page générée obsolète. Voir Écrire la documentation.

#Contrôles transverses

Contrôle Outil Seuil
Secrets dans tout l'historique Git gitleaks 8.30.1, configuration .gitleaks.toml tout secret détecté hors liste blanche
Validité de docker-compose.yml docker compose --profile app config -q erreur de syntaxe ou de référence
Construction des images backend (cible runtime), frontend web, blockchain locale, Office de Tourisme échec de construction
Vulnérabilités des images Trivy 0.76.2 sur les images backend, web et tourisme, --ignore-unfixed toute vulnérabilité HIGH ou CRITICAL corrigeable
Analyse statique de sécurité CodeQL, requêtes security-extended alerte de sécurité

La liste blanche de gitleaks ne contient que deux valeurs publiques de développement, refusées par le backend en production : la clé ENCRYPTION_KEY de démonstration et la clé privée du compte Hardhat n° 0. L'image de la blockchain locale n'est pas analysée par Trivy : elle sert au développement et à la CI, jamais en production.
