Standards de code

Ces règles s'appliquent à tout le code livré dans le dépôt. Une partie est vérifiée automatiquement (TypeScript strict, ESLint, solhint, synchronisation de .env.example), le reste relève de la revue. Les conventions d'organisation propres à chaque projet (découpage en modules, nommage des fichiers) sont détaillées dans Conventions de code.

#Règles communes

Règle Portée Vérification
TypeScript en mode strict backend, frontend web, mobile, scripts des contrats strict: true dans chaque tsconfig.json, npm run typecheck en CI
Aucun commentaire de code tout le code livré revue
Aucun émoji, ni dans le code ni dans les messages tout le dépôt revue
Indentation de 2 espaces, fin de ligne LF, encodage UTF-8, saut de ligne final tous les fichiers .editorconfig, .gitattributes
Textes destinés aux utilisateurs en français messages d'erreur de l'API, interfaces revue
Aucun secret dans le dépôt tout l'historique Git gitleaks en CI, avec .gitleaks.toml

#Pas de commentaires

Le code ne contient pas de commentaires explicatifs : les noms de variables, de fonctions et les tests portent l'intention. Une fonction qui a besoin d'un commentaire pour être comprise doit être renommée ou découpée. L'explication des choix revient à la documentation et aux ADR.

Trois exceptions sont nécessaires au fonctionnement des outils :

Exception Pourquoi
// SPDX-License-Identifier: MIT en tête des fichiers Solidity Exigé par le compilateur, qui avertit en son absence
Blocs /** @openapi ... */ au-dessus des routes Express Lus par swagger-jsdoc pour la page /api/docs, et par le générateur de la Référence de l'API, qui en extrait le summary
Directives d'outils (eslint-disable) À éviter ; si inévitable, limitées à une ligne et justifiées dans la pull request

#Pas d'émojis

Ni dans le code, ni dans les messages d'API, ni dans les interfaces, ni dans les commits. Les icônes de l'interface sont des SVG.

#Backend

#Organisation d'un module

Chaque domaine de backend/src/api/ suit le même découpage en cinq fichiers, par exemple pour les partenaires :

Fichier Responsabilité Ne doit pas
partners.routes.ts Déclarer les routes, empiler les middlewares (authenticate, requireRoles, validate, idempotency), porter le bloc @openapi contenir de logique métier
partners.validators.ts Schémas Zod de body, query et params accéder à la base
partners.controllers.ts Lire la requête, appeler le service, répondre avec sendSuccess, transmettre les erreurs à next contenir de requête Prisma
partners.services.ts Règles métier, contrôles d'accès fins, orchestration manipuler req ou res
partners.repo.ts Requêtes Prisma contenir de règle métier

Chaque fichier exporte une instance unique (export const partnersService = new PartnersService()) et l'exporte par défaut. Le guide Ajouter un endpoint montre le découpage sur un exemple complet.

#Réponses et erreurs

Règle Outil
Réponse réussie : { success: true, message, data, meta? } sendSuccess(res, data, message, statusCode, meta) de response.util.ts
Erreur métier : lever une AppError(message, statusCode, details) Convertie en réponse { success: false, message, errors } par error.middleware.ts
Erreur de validation : 400 avec la liste { path, message } validate.middleware.ts
Erreur d'un contrat : décodée et traduite en message français avec un statut HTTP toAppError de lottery.gateway.ts

Un contrôleur entoure toujours l'appel du service d'un try et passe l'erreur à next(error). Le format complet est décrit dans Réponses et erreurs.

#Promesses

Toute promesse est attendue (await) ou explicitement ignorée avec void. ESLint l'impose dans src/ et prisma/ avec @typescript-eslint/no-floating-promises en erreur (backend/eslint.config.mjs) :

TypeScript
void lotteryIndexer.syncOnce();

Une promesse lancée en arrière-plan doit traiter son propre échec, sans quoi une erreur non gérée arrête le processus :

TypeScript
walletService
  .grantWelcomeEthers(user)
  .catch((error: Error) => logger.warn(`Dotation de bienvenue différée : ${error.message}`));

#Configuration

  • process.env n'est lu que dans backend/src/config/. Le reste du code importe env depuis env.config.ts, déjà typé et validé.
  • Toute nouvelle variable est ajoutée au schéma Zod et à backend/.env.example ; npm run env:check vérifie la synchronisation. La procédure complète est dans Ajouter une variable d'environnement.

#Appels sortants

Chaque appel vers un service extérieur a un délai maximal. C'est le cas aujourd'hui :

Service Délai Fichier
PostgreSQL statement_timeout (DB_STATEMENT_TIMEOUT_MS, 15 s), lock_timeout 5 s, idle_in_transaction_session_timeout 60 s, délai de connexion DB_CONNECTION_TIMEOUT_MS prisma.config.ts
Redis 1 s par défaut pour la connexion et le PING redis.config.ts
SMTP connexion et accueil 10 s, socket 20 s mailer.config.ts
RPC Ethereum 15 s par requête (RPC_TIMEOUT_MS) chain.client.ts
S3 connexion 3 s, requête 10 s s3.service.ts

Un nouveau client HTTP ou SDK doit recevoir un délai du même ordre.

#Journalisation

Les journaux passent par logger.util.ts (winston), jamais par console.log dans src/. Une adresse email est masquée avec maskEmail avant d'être journalisée ; une clé privée, un jeton ou un code à usage unique ne sont jamais journalisés.

#Migrations

Toute migration Prisma respecte l'ADR 0003 : expand/contract, SET lock_timeout = '5s' en première ligne, contraintes ajoutées en NOT VALID puis validées. Voir Ajouter une migration et Migrations expand et contract.

#Smart contracts

Règle Détail
solhint recommended, zéro avertissement smart-contract/.solhint.json, npm run lint
Version du compilateur ^0.8.28 imposée par solhint, compilation en 0.8.34 avec l'EVM prague et l'optimiseur à 200 exécutions (hardhat.config.ts)
Erreurs personnalisées gas-custom-errors en erreur : revert NomErreur(...), jamais require(condition, "message")
Imports nommés no-global-import en erreur : import {AccessControl} from "..."
Visibilité explicite func-visibility en erreur, constructeurs exclus
Fonds modèle de retrait (claimPrize, claimRefund), checks-effects-interactions et nonReentrant sur toute fonction qui envoie des ethers
Couverture 100 % des lignes des contrats de production

Règles volontairement désactivées dans .solhint.json : reason-string (remplacé par les erreurs personnalisées), not-rely-on-time (les tours sont bornés par block.timestamp), avoid-low-level-calls (les versements utilisent call), use-natspec, gas-indexed-events, gas-strict-inequalities et gas-struct-packing.
