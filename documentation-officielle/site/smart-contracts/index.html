4. Smart contracts

Vue d'ensemble

Le cœur de BlockLucky est un vrai smart contract Solidity. Il reçoit les mises des citoyens, tire le gagnant avec Chainlink VRF et garde la cagnotte jusqu'à son retrait. Un second contrat délivre un badge de participation non transférable. Le backend ne fait qu'appeler ces contrats et indexer leurs événements : il ne choisit jamais le gagnant et ne détient jamais la cagnotte.

Le projet Hardhat se trouve dans smart-contract/. Il a été écrit pour répondre au brief du kickoff : « créer un smart contract pour une loterie simple », avec des tickets achetés en ethers fictifs et un gagnant tiré au hasard après un certain nombre de participants ou une certaine durée. La décision et ses alternatives sont tracées dans l'ADR 0004.

#Les deux contrats

Contrat Fichier Rôle Hérite de
BlockLucky smart-contract/contracts/BlockLucky.sol Loterie par tours successifs : achat et cadeau de tickets en ethers, tirage Chainlink VRF, cagnotte et remboursements en retrait, commission de la Mairie, disjoncteur VRFConsumerBaseV2Plus, AccessControl, Pausable, ReentrancyGuard, AutomationCompatibleInterface
BlockLuckyPOAP smart-contract/contracts/BlockLuckyPOAP.sol Badge ERC-721 non transférable (« soulbound »), un par participant et par tour, frappé par l'opérateur ERC721, AccessControl

Deux contrats supplémentaires, ReentrantPlayer.sol et RejectingPlayer.sol, ne servent qu'aux tests : le premier tente une réentrance, le second refuse tout paiement. Ils ne sont jamais déployés hors des tests.

Les deux contrats de production sont indépendants : BlockLucky ne connaît pas BlockLuckyPOAP. C'est le backend qui frappe un badge après un achat, par sa file d'actions on-chain.

#Place dans l'architecture

flowchart LR
    citoyen["Portefeuille intégré du citoyen"] -->|"buyTickets, claimPrize, claimRefund"| lottery["BlockLucky"]
    operateur["Compte opérateur du backend"] -->|"cancelRound, pause, withdrawFees"| lottery
    keeper["Keeper du backend ou Chainlink Automation"] -->|"requestDraw, closeExpiredRound"| lottery
    lottery -->|"requestRandomWords"| coord["Coordinateur Chainlink VRF v2.5"]
    coord -->|"rawFulfillRandomWords"| lottery
    operateur -->|"mintBadge"| poap["BlockLuckyPOAP"]
    lottery -.->|"événements"| indexeur["Indexeur du backend"]
    lottery -->|"withdrawFees"| tresor["Trésorerie de la Mairie"]

Les achats sont signés par le portefeuille Ethereum que le backend crée pour chaque citoyen (voir les portefeuilles intégrés). Les actions d'exploitation sont signées par le compte opérateur (RELAYER_PRIVATE_KEY, voir le client RPC). Le keeper du backend surveille isDrawReady et isExpiredWithoutDraw et déclenche le tirage ou l'annulation. L'indexeur reconstruit la base à partir des événements.

#Ce que garantit le contrat

Garantie Mécanisme Page
Le gagnant n'est choisi ni par la Mairie ni par le backend Mot aléatoire Chainlink VRF v2.5, randomWords[0] % ticketCount Tirage Chainlink VRF
Le tirage ne peut pas être bloqué par le backend requestDraw et closeExpiredRound sont appelables par tous dès que les conditions sont remplies Cycle de vie d'un tour
Les fonds ne restent jamais bloqués Retrait de la cagnotte et des remboursements à l'initiative du bénéficiaire, annulation avec remboursement intégral Contrat BlockLucky
La commission de la Mairie est bornée 10 % par défaut, refus au-delà de 20 % (MAX_FEE_BPS = 2000) Contrat BlockLucky
La réentrance est impossible Checks-effects-interactions et nonReentrant sur chaque fonction qui déplace des fonds Sécurité du contrat
Les droits sont séparés DEFAULT_ADMIN_ROLE, OPERATOR_ROLE, PAUSER_ROLE Exploitation du contrat
Un oracle muet ne fige pas un tour retryDraw après drawTimeout, ou cancelRound Tirage Chainlink VRF

Analyse statique solhint sans avertissement, Slither bloquant dès le niveau Medium
Paramètres par défaut d'un tour 0,01 ETH le ticket, 10 000 tickets, 2 tickets minimum, 100 par participant, 10 % de commission

Important

À la date de rédaction, aucun déploiement Sepolia n'est enregistré dans le dépôt : aucun fichier smart-contract/deployments/sepolia.json n'est versionné. Les scripts Sepolia (abonnement VRF, déploiement avec séparation des rôles, upkeep Automation, vérification Etherscan) existent et sont documentés, mais ils demandent les clés et les fonds de test de l'équipe : portefeuille de déploiement, multisig de la Mairie, ETH et LINK de test, accès RPC, clé Etherscan.

#Commandes du projet

Toutes se lancent depuis smart-contract/ après npm ci (Node.js 22.12 ou plus récent, voir engines dans package.json).

Commande Effet
npm run build Compile les contrats (hardhat build)
npm run typecheck Compile puis vérifie le TypeScript des scripts et des tests
npm run lint solhint sur contracts/*.sol, zéro avertissement toléré
npm test Lance les tests Solidity puis Mocha
npm run test:coverage puis npm run coverage:check Mesure la couverture et échoue sous 100 % des lignes
npm run test:gas Coût en gaz de chaque fonction appelée par les tests
npm run slither Slither 0.11.6 dans Docker
npm run node Démarre un nœud Hardhat local
npm run deploy:local Déploie sur le nœud local
npm run vrf:sepolia Crée ou recharge l'abonnement VRF Sepolia, financé en ETH (setup-vrf-sepolia.ts)
npm run deploy:sepolia Déploie sur Sepolia et répartit les rôles (deploy-sepolia.ts)
npm run automation:sepolia Inscrit l'upkeep Chainlink Automation (register-automation-sepolia.ts)
npm run verify:sepolia Publie le code des deux contrats sur Etherscan (verify-sepolia.ts)
npm run export:abi Copie les ABI dans backend/src/blockchain/abi/
