3. Architecture

Vue d'ensemble

Cette page décrit l'architecture de BlockLucky selon le modèle C4, du plus large au plus détaillé : le contexte (qui utilise le système et avec quels systèmes externes il échange), les conteneurs (les applications et les stockages qui tournent), puis les composants du backend. Les diagrammes sont écrits en Mermaid dans les sources de la documentation : ils se modifient dans la même pull request que le changement d'architecture qu'ils décrivent.

Trois idées structurent l'ensemble :

  • La blockchain est la source de vérité de la loterie. Les tickets, le tirage, la cagnotte et les remboursements vivent dans le contrat BlockLucky. La base PostgreSQL en est une projection, reconstruite par un indexeur d'événements.
  • Le citoyen n'installe aucun portefeuille. Le backend crée et chiffre un portefeuille Ethereum par citoyen, signe ses transactions et lui verse une dotation d'ethers fictifs (voir l'ADR 0004).
  • Un seul backend, deux process. L'API HTTP et le worker sont construits depuis la même image et le même code (voir l'ADR 0001).

#Répartition entre l'API et le worker

Le process API (backend/src/server.ts) démarre Express, Socket.IO et le pont d'événements Redis. Il ne démarre les workers BullMQ et les services de chaîne (indexeur et keeper) que si RUN_WORKERS=true, la valeur par défaut du schéma de configuration. Docker Compose fixe RUN_WORKERS: "false" pour le service backend et lance un service worker séparé.

Le process worker (backend/src/worker.ts) démarre toujours startWorkers() et startChainServices(). Il s'arrête avec un code d'erreur si aucun worker n'a pu être créé, et expose /health/live et /metrics sur le port PORT + 1.

Traitement Process API (RUN_WORKERS=false) Process worker Process API seul (RUN_WORKERS=true)
Requêtes REST et Socket.IO oui non oui
Workers emails-queue, ledger-queue, chain-actions non oui oui
Indexeur (lotteryIndexer.syncOnce, toutes les INDEXER_INTERVAL_MS) non oui (mode onchain) oui (mode onchain)
Keeper (runKeeperOnce, toutes les KEEPER_INTERVAL_MS) non oui (mode onchain) oui (mode onchain)
Indexation immédiate du reçu d'une transaction envoyée par l'API oui - oui

L'indexeur et le keeper sont démarrés par startChainServices dans backend/src/blockchain/lottery.keeper.ts. Ils ne font rien en mode simulated. Le détail est dans Indexeur d'événements et Keeper du tirage.

#Relais des événements temps réel

Les événements draw:winner et points:awarded sont produits par l'indexeur, donc souvent dans le worker, qui n'a pas de serveur Socket.IO. emitSocketEvent (backend/src/socket/event-bridge.ts) émet directement si le process possède un serveur Socket.IO, sinon publie le message sur le canal Redis <REDIS_KEY_PREFIX>:<NODE_ENV>:socket-events. L'API s'y abonne au démarrage (startSocketEventBridge) et réémet vers tous les clients connectés, en ne laissant passer que ces deux événements. Voir Relais temps réel.

Attention

Socket.IO n'utilise pas d'adaptateur Redis. Les événements émis directement par une instance d'API (salle d'attente, chat) n'atteignent que les clients de cette instance. Le passage à plusieurs instances d'API demande l'ajout de @socket.io/redis-adapter ou équivalent.

#Modes de fonctionnement

BLOCKCHAIN_MODE (backend/src/config/env.config.ts) vaut onchain par défaut et est imposé en production par le schéma Zod. En mode simulated, les services de backend/src/services/blockchain.service.ts génèrent des hash aléatoires, tirent le gagnant avec crypto.randomInt et ne versent aucune cagnotte. Ce mode sert aux tests unitaires et au développement sans nœud. Voir Mode onchain ou simulé.

#Chaîne HTTP

backend/src/app.ts monte les middlewares dans cet ordre :

  1. requestContextMiddleware : identifiant X-Request-Id propagé dans les logs par AsyncLocalStorage (backend/src/observability/request-context.ts).
  2. httpMetricsMiddleware : histogrammes Prometheus par route (backend/src/observability/metrics.ts).
  3. Helmet, CORS limité à FRONTEND_URL et CORS_ORIGINS, express.json limité à 1 Mo (corps brut conservé pour /api/webhooks/*), express.urlencoded.
  4. Routes système (/health, /health/live, /health/ready, /health/deep, /api/config) et /metrics, avant le mode maintenance et le rate limit.
  5. Mode maintenance : MAINTENANCE_MODE=true renvoie 503 avec Retry-After: 300 sur /api/* sauf /api/admin.
  6. globalRateLimiter : 300 requêtes par 15 minutes et par IP, compteurs dans Redis.
  7. Swagger sur /api/docs, puis le routeur des modules monté sur /api/v1 et /api.
  8. notFoundHandler et errorHandler.

Dans chaque route, les middlewares spécifiques suivent l'ordre authenticate, requireRoles, idempotency, validate, puis le controller. Le détail est dans Structure et cycle d'une requête.
